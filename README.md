# Local AI Workspace

**低配置电脑，也能探索大参数模型的本地运行。**

Local AI Workspace 是面向 Windows 的本地 AI 工作区，以 Intel Core i5-1235U、16 GiB 内存、Intel UHD 核显作为参考实验平台，将 Qwen3 8B、Gemma 3 27B、Llama 3.3 70B 三档模型的本地推理、桌面交互与资源管理组织成完整流程。

项目关注普通电脑运行大模型时的实际问题：权重文件怎样压缩、有限内存怎样安排、模型切换后怎样释放资源，以及一次回答到底花了多少时间。通过低比特量化、CPU 内存映射、70B 分层读取和运行日志，让已有设备能够完成可观察、可取消、可复查的本地 AI 实验。

[项目博客](https://avasubaru486.github.io/blog/local-ai-workspace/) · [个人主页](https://avasubaru486.github.io/) · [下载源码与演示](https://github.com/AvaSubaru486/LocalAIWorkspace/archive/refs/heads/main.zip)

## 项目定位：在有限资源中完成大模型推理

参考机的三档文字路径使用 CPU 计算，独立显卡和大显存没有被列为这条路径的前提。模型文件与依赖准备完成后，回答由本机权重生成；计算速度、内存余量、SSD 读取能力和上下文长度共同决定等待时间。

8B 用来观察较轻量的文字交互，27B 扩展到更大的参数规模与配套图片输入，70B 用来探索权重难以同时驻留内存时的运行能力。三档模型串行执行，便于在同一设备上比较启动等待、生成速度、资源占用和任务结束状态。

项目的工程重点是把模型加载、资源预算、聊天界面与实验记录整合起来。基础模型、量化权重与推理组件来自各自的上游项目，具体来源见文末。

## 可以做什么

- 在同一桌面界面完成文字聊天、历史会话、附件输入与 Python 工作区操作。
- 切换三档本地模型，管理请求取消、内存预算与模型进程回收。
- 使用 Gemma 3 27B 与配套视觉组件处理图片、分析视频抽样帧。
- 导出运行日志 ZIP，统一记录设备、模型哈希、首字时长、解码速度、内存及结束状态，供跨设备实验比较。
- 在包含运行时和模型的完整便携包中，解压后双击 `LocalAIWorkspace.exe` 启动。

## 三档模型

| 模型 | 本版量化 | 权重体积（十进制） | 运行路径 |
| --- | --- | ---: | --- |
| Qwen3 8B | UD-IQ2_XXS | 2.61 GB | CPU 内存映射，轻量文字交互 |
| Gemma 3 27B | UD-IQ1_S | 6.51 GB | CPU 内存映射，支持配套视觉组件 |
| Llama 3.3 70B | UD-IQ1_S | 15.85 GB | 分层 CPU 读取，大参数模型运行探索 |

27B 的视觉组件另占约 0.86 GB，完整 ZIP 为 **29,697,284,670 字节**。本地推理使用电脑自身资源；模型、推理后端与第三方依赖沿用各自的许可证。

## 低配置运行大模型的实现方式

### 1. 低比特量化：先减少权重的存储开销

如果只按 70B 参数、每个参数用 2 字节表示粗略估算，权重规模约为 140 GB，运行时还需要额外的缓存与缓冲空间。本版采用的 Llama 3.3 70B UD-IQ1_S 权重实际为约 15.85 GB，即 14.77 GiB，给本地存储与后续读取提供了更紧凑的输入。

量化改变权重数值的表示精度，参数规模、文件体积与回答质量需要分别考察。UD-IQ2_XXS、UD-IQ1_S 是具体量化方案名称，实际文件还包含结构信息和其他开销，体积以清单中的文件字节数为准。低比特带来的回答质量取舍，仍需通过固定任务的成对评估持续测量。

### 2. 8B / 27B 内存映射：按实际访问读取页面

两档文字路径将模型文件映射到进程地址空间，由系统按访问需求调入页面。配套低内存后端关闭整文件预取，应用根据启动时可用内存和设置计算驻留预算。内存足够时，已访问的页面可以留在内存中供后续计算使用；页面频繁被回收时，磁盘访问与等待会增加。

映射的文件大小、进程地址空间和此刻驻留在物理内存中的页面属于不同概念。模型占用需要结合实际工作集、私有提交量和系统剩余内存一起看。

### 3. 70B 分层读取：让 SSD 与有限内存协作

70B 使用原便携版配套的专用低内存 CPU 后端，按计算阶段读取各层权重。应用设置分层文件路径、无缓冲和直接读取请求，并检查后端日志中的启用标记；配置未按预期生效时停止启动。

完整权重保存在 SSD，计算需要的部分进入有限的内存工作集，再由 CPU 执行。生成过程会继续经过模型各层，权重无法充分缓存时会反复读取文件，因此 SSD 吞吐、读取延迟与后台磁盘负载会直接影响生成时间。这种路径通过更多读取与等待，换取更低的同时驻留需求。

应用层实现见 [cpu_compatibility.py](app/cpu_compatibility.py) 和 [models.py](app/models.py)。公开仓库发布应用源码与配置；复现这条分层路径时，还需要准备与清单匹配的低内存推理后端。

### 4. 内存预算与进程回收：管理一次任务的完整生命周期

启动前读取系统可用内存与用户设置，分别计算私有提交预算和驻留工作集预算；70B 的驻留配置上限为 4 GiB，默认模型进程提交预算为 12 GiB。这两类上限采用不同统计口径，整机占用还包含系统、桌面界面、文件缓存和运行缓冲，实际数值以日志为准。

模型及其子进程纳入 Windows Job Object 管理，运行期间持续观察内存；超出自身预算时停止任务并记录原因。切换模型、取消请求和退出应用时回收对应进程，避免多个大型模型同时驻留。实现见 [memory_limits.py](app/memory_limits.py) 和 [windows_job.py](app/windows_job.py)。

### 5. 控制上下文、输出与并发

本版文字路径默认 4 个推理线程、2048-token 上下文、每轮最多 256 个新 token，三档模型串行执行。上下文还会占用运行缓存，长提示、长历史会话与长输出都会增加资源开销和等待。

下面的实机演示使用 512-token 上下文、最多生成 64 tokens，与默认运行参数分别记录。复现实验时需要同时固定模型版本、量化、后端、线程、上下文和实际输出长度。

## 怎样理解“低配置运行”

| 组成 | 在本项目中的作用 |
| --- | --- |
| CPU | 执行本版三档模型的文字推理；参考处理器为 i5-1235U |
| 内存 | 容纳当前计算需要的页面、上下文缓存及运行缓冲；参考机为 16 GiB |
| 核显 | 参考设备使用 Intel UHD；本版文字路径采用 CPU |
| SSD | 保存模型权重，承担按需调入与 70B 分层读取 |
| 单任务调度 | 同一时间串行执行模型任务，切换后回收旧进程 |

配置清单为 70B 标注了 24 GiB 起、32 GiB 推荐内存。16 GiB 参考机完成过下述短任务，属于受限条件下的运行记录；其他设备还需要结合可用内存、存储性能与具体任务验证。

一次短回答可以验证加载与推理链路能否完成；持续对话需要进一步测量长上下文、长输出和重复运行表现；回答质量还需要单独评估。项目把这几个维度放进同一套日志流程，帮助判断某个模型适合怎样的任务。

## 仓库结构

```text
app/             桌面交互、模型调度、内存预算与运行日志
config/          固定模型版本、下载来源、SHA-256 与运行参数
scripts/         构建、校验与原项目的实验脚本
launcher/        Windows 启动器源码
resources/       项目资源与知识库来源配置
data/            模型清单及附带的知识库资料
docs/            使用指南、技术说明和第三方许可
demo/            原理动画、三模型实机演示视频
```

源码仓库不包含大型模型、Python/Qt/CUDA 运行时或编译后的应用。原始压缩包中的文档说明保留在 [docs/BUNDLED-README.md](docs/BUNDLED-README.md)。
